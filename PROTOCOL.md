# Eval receipt protocol v1

Protocol identifier: `creationloop.eval.v1`. SHA-256 throughout. JSON canonicalization is UTF-8 with sorted object keys, compact separators, literal Unicode, and finite values. Duplicate JSON object keys, duplicate item ids, unknown item keys, booleans as scores, NaN/Infinity and empty files are refused. Item scores and optional USD costs become decimal strings with at most 12 fractional places. JSON input/output values retain their JSON types; CSV input/output are strings. Unicode is preserved without normalization.

Every item receives an independent 32-byte cryptographic random salt. For zero-based index `i`, the leaf is SHA256(`creationloop.eval.item.v1\0` || salt bytes || canonical JSON `{"index":i,"item":normalized_item}`). An interior node is SHA256(`creationloop.eval.node.v1\0` || left32 || right32). At an odd-width level, the last node is duplicated. There is no empty-tree root. Inclusion proofs contain exactly one oriented sibling per level; position, length, duplicate-last behavior and root are checked.

`items.jsonl` stores item, index and salt. `proofs.jsonl` stores index and siblings. These private local files plus `receipt.json` are needed to recompute the whole run. `root.bin` contains the raw 32-byte root. All artifact files are created at mode 600 and the output directory at mode 700 on POSIX. Existing output directories are refused to preserve evidence. A retry publishes the same `receipt.json` and run UUID rather than repeating `receipt eval`.

The aggregate is the arithmetic mean of all item scores, with exact decimal summation and half-even rounding to 12 fractional places. The wire summary contains count, decimal sum, mean, sorted unique model/grader names and a nullable USD total. Scores need not be binary or fall within 0..1. Missing names become `unspecified`. Optional `--model`/`--grader` may fill missing names but cannot contradict names in the file. `--share-cost` is required to transmit any cost total; item costs always stay local.

The strict wire schema contains only `schema`, `kind`, random `run_id`, `suite_hash`, `config_hash`, `models`, `graders`, and `run_metadata`, plus a settlement's `root`, `summary`, `seed_id`, or a seed's `expires_at`. `run_metadata` contains only UTC `created_at`, `demo`, `tool_version`, optional public `benchmark_hash` and, since tool 0.1.1, optional `model_fingerprints`. This last field maps only model names already in the run to lowercase 64-character SHA256 weights fingerprints. The caller opts in with `--weights-fingerprint MODEL=SHA256`; no files or per-component hashes are uploaded. It is committed in the immutable seed/settlement ledger entry, must match pre-registration, and is checked by online verification. The CLI validates its format and commitment; verifying that particular weights actually executed requires separate observed runtime evidence. No filename, path, arbitrary tags, user identity, input, output, id, salt, item hash list or item proof is accepted. Authentication is a separate bearer header; keys are absent from URLs and metadata. Tool 0.1.1 verifies unchanged 0.1.0 receipts; fingerprint receipts require the 0.1.1 verifier.

The suite commitment is a length-prefixed hash stream of ordered index/id/input pairs, prefixed with `creationloop.eval.suite.v1\0` and a stable secret local suite salt. Config is SHA256(`creationloop.eval.config.v1\0` || private random config salt || canonical local config). The suite salt persists in the local settings directory and stays on that machine. Series identity is SHA256(`creationloop.eval.series.v1\0` || canonical `{suite_hash,models}`). Consequently series continuity is scoped to that local suite commitment; a different installation has a different commitment. Grader/config changes remain visible per run without resetting a suite/model series.

Pre-registration reserves a UUID and run number before inference. A settlement must bind the same ordered suite, model, grader and config commitments and demo/benchmark labeling. Expired seeds cannot settle and remain in the numbered series as abandoned. An idempotent retry never allocates another number. `series_total` is the current total of all registered runs, including abandoned seeds, and increases as new runs register. A receipt originally showing run 1 of 1 later shows run 1 of 2.

Ledger entries carry segment `eval-receipts-v1`, sequence, previous hash, timestamp, event, run id, series id, number and payload. Entry hash is SHA256(`creationloop.eval.ledger.v1\0` || canonical entry without its hash). Genesis previous hash is 64 zeroes. The private registry owns this separate segment. It never writes Builder A's lane. Its JSONL export can be checked and imported by that lane later through a separately authorized importer.

The OpenTimestamps detached proof timestamps SHA256(`root.bin`). Calendar submissions contain only that digest. Standard proof operations bind it to a Bitcoin block Merkle root. A seed independently timestamps its ledger-entry digest, saved as the 32-byte file digest input using the same root.bin convention. The open verifier validates the proof's initial SHA256 digest, Bitcoin Merkle root, header hash, proof of work and agreement of two independently queried HTTPS main-chain witnesses. The official `ots` client can also verify the downloaded `.ots` with Bitcoin Core and `root.bin`. A pending attestation is never confirmation.

Endpoints (all authenticated, under the private registry prefix): `POST /api/seed`, `POST /api/settle`, `GET /api/runs/<run_id>`, `GET /api/ledger/<entry_hash>`, `GET /proof/<run_id>`, `GET /r/<run_id>`, and `GET /api/health`. Mutating APIs require bearer authentication; browser cookie sessions are read-only. Redirects are refused by the CLI before credentials can follow them. Receipt-provided origins cannot override the user's configured registry.
